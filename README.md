# VNEngine

**VNEngine** — экспериментальный JavaScript-движок для создания визуальных новелл и интерактивных историй.

Проект строится вокруг идеи **минимального ядра и расширяемой plugin-first архитектуры**: ядро отвечает за выполнение истории, а игровые механики и визуальное поведение реализуются отдельными плагинами.

## Основная идея

VNEngine разделяет выполнение истории и её игровые механики.

Ядро отвечает за:

* загрузку проекта;
* переход между узлами истории;
* ожидание и продолжение выполнения;
* регистрацию обработчиков типов узлов;
* события жизненного цикла истории.

Плагины отвечают за конкретные возможности игры:

* диалоги;
* повествование;
* фон;
* ожидание;
* выборы;
* состояние игры;
* условия;
* и другие механики, которые могут появиться позже.

Это позволяет не превращать ядро в набор знаний обо всех возможных игровых механиках.

## Архитектура

Упрощённо система выглядит так:

```text
Project  (сцены, узлы, config, список плагинов)
   │
   ▼
loadProjectPlugins ──► PluginRegistry ──► загрузчик (plugins/<имя>-plugin.js)
   │   порядок по dependencies
   ▼
PluginManager ──── VN ──── EventBus
   │
   ├── StatePlugin
   ├── ConditionsPlugin
   ├── DialoguePlugin
   ├── NarrationPlugin
   ├── BackgroundPlugin
   ├── WaitPlugin
   ├── ChoicePlugin
   └── TopLeftHUDPlugin
```

### VN

`VN` — исполнитель истории.

Он не знает, что такое диалог, выбор, состояние или условие. Для него существует только последовательность узлов и зарегистрированные обработчики их типов.

Обработчик узла получает контекст:

```js
{
    wait(),
    resume(),
    goto(nodeId)
}
```

### Project

`Project` является единым источником данных игры.

В нём находятся:

* сцены;
* узлы;
* конфигурация;
* ресурсы;
* начальные данные проекта;
* список плагинов, которые нужны проекту (`plugins`).

Runtime-состояние при этом хранится отдельно от `Project`.

### PluginManager

`PluginManager` устанавливает плагины и предоставляет им единый API.

Плагины могут предоставлять собственный публичный API другим плагинам:

```js
api.plugins.state.api.get();
api.plugins.conditions.api.evaluate(condition, state);
```

Таким образом, взаимодействие между плагинами происходит через явно определённые публичные интерфейсы.

### Загрузка плагинов

Проект сам перечисляет нужные плагины по именам, а движок получает их и ставит в правильном порядке:

```js
const project = new Project({
    plugins: ['state', 'conditions', 'dialogue', 'choice'],
    scenes: [/* ... */]
});

const registry = new PluginRegistry({ loader: localPluginLoader });

await loadProjectPlugins(project, registry, plugins);

game.loadProject(project);
```

Что происходит внутри:

1. `project.getPlugins()` отдаёт имена (строки или `{ name, version }`).
2. `PluginRegistry.resolve()` по имени получает плагин: проверяет имя, при необходимости вызывает загрузчик (`localPluginLoader` читает `plugins/<имя>-plugin.js`) и проверяет, что загружен именно тот плагин.
3. `orderPlugins()` сортирует плагины так, чтобы зависимости шли раньше зависимых. Нехватка зависимости или цикл дают понятную ошибку.
4. `PluginManager.use()` ставит плагины по одному. Если установка падает, уже установленные плагины удаляются.

Порядок плагинов в списке проекта не важен: он определяется `dependencies`. Загрузчик можно заменить другим (например, получающим плагины из сервиса): интерфейс `resolve()` асинхронный.

Схемы: `diagrams/plugin-loading-flow.excalidraw` (загрузка) и `diagrams/vnengine-structure.excalidraw` (структура проекта), открываются в Excalidraw.

### EventBus

`EventBus` используется для событий и фактов, происходящих в системе.

Например:

```js
story:loaded
node:start
story:end
```

События не являются системой навигации. Переходы между узлами выполняются самим `VN`.

### BlockManager

`BlockManager` управляет визуальными блоками, создаваемыми плагинами.

Блок содержит:

```js
{
    id,
    type,
    channel,
    state,
    element,
    data,
    meta
}
```

Это позволяет разным плагинам работать с визуальными элементами, не зная внутренней реализации друг друга.

## Плагины

Плагин имеет минимальный контракт:

```js
export const ExamplePlugin = {
    name: 'example',
    version: '0.1.0',
    dependencies: [],
    nodeTypes: ['example'],

    install(api) {
        return {
            api: {
                // публичный API плагина
            },

            cleanup() {
                // освобождение ресурсов
            }
        };
    }
};
```

Имя плагина совпадает с названием файла (`example` → `plugins/example-plugin.js`), плагин экспортируется через `export default`. Готовый шаблон: `templates/plugin-template.js`.

Плагин может:

* регистрировать типы узлов;
* создавать визуальные блоки;
* подписываться на события;
* предоставлять публичный API;
* использовать API других плагинов.

Игровая механика не должна попадать в ядро без необходимости.

## Состояние игры

Runtime-состояние принадлежит `StatePlugin`.

Начальные значения могут находиться в конфигурации проекта:

```js
const project = new Project({
    config: {
        state: {
            health: 3,
            money: 100
        }
    }
});
```

После загрузки проекта `StatePlugin` получает начальные данные через событие:

```text
Project
   │
   │ story:loaded
   ▼
StatePlugin
   │
   ▼
runtime state
```

Другие плагины работают с состоянием через его публичный API:

```js
const state =
    api.plugins.state.api.get();

api.plugins.state.api.set(
    'health',
    10
);
```

`Project` и runtime-состояние являются разными сущностями.

## Условия

Проверка игровых условий реализована отдельным `ConditionsPlugin`.

Например:

```js
{
    variable: 'health',
    operator: '>',
    value: 5
}
```

Плагин предоставляет:

```js
api.plugins.conditions.api.evaluate(
    condition,
    state
);
```

На текущем этапе поддерживаются операторы:

```text
==
!=
>
>=
<
<=
```

## Выборы

Выбор является отдельным типом узла и реализуется `ChoicePlugin`.

Один логический вариант может иметь несколько вариантов результата в зависимости от состояния:

```js
{
    id: 'go',
    variants: [
        {
            condition: {
                variable: 'health',
                operator: '<=',
                value: 5
            },
            text: 'Сначала в больницу',
            goto: 'hospital'
        },
        {
            condition: {
                variable: 'health',
                operator: '>',
                value: 5
            },
            text: 'Пойдём домой',
            goto: 'home'
        }
    ]
}
```

`ChoicePlugin` определяет подходящий вариант через `ConditionsPlugin`, а затем выполняет переход через API ядра:

```js
context.goto(nodeId);
```

## Проверка проекта

Перед запуском проект проверяет `ProjectValidator`. Ошибки блокируют запуск, предупреждения нет.

```js
const validator = new ProjectValidator(bus);

const result = await validator.validate(project, {
    plugins: plugins.getManifests()
});

if (!result.valid) {
    // result.errors, result.warnings
}
```

Каждая запись содержит `code`, `message`, `path`, `plugin` и `severity` (`error` или `warning`).

Плагин добавляет свои проверки через `api.validation`; при удалении плагина они исчезают:

```js
api.validation.register({
    id: 'items',
    run(project, context) {
        return [{ code: 'inventory.empty', message: 'Нет предметов', path: 'config.items' }];
    }
});

// правило только для узлов одного типа
api.validation.registerNodeRule('choice', {
    id: 'options',
    run(node) {
        return node.options ? [] : [{ message: 'У choice нет options' }];
    }
});
```

Проверка, которая упала или не уложилась в 3 секунды, превращается в предупреждение `check.crashed` или `check.timeout` и не мешает остальным.

## Документация

API проекта документируется непосредственно в исходном коде и генерируется с помощью `apiscribe`.

Исходный код и API-комментарии являются единым источником истины для документации.

Для комментариев в формате `apiscribe` используйте простые типы (`string`, `Object`, `Object[]`, `Promise`): вложенные фигурные скобки и угловые скобки внутри `{...}` парсер не понимает.

## Статус проекта

VNEngine находится в стадии активной разработки.

Архитектура сейчас важнее количества реализованных игровых механик: цель ранних версий — сформировать устойчивое ядро, вокруг которого можно безопасно развивать плагины и инструменты.
